# Mechanism: the public skill showcase

## What it is

The browsable marketplace website at GitHub Pages, generated from `catalog.json`. One
source of truth, no hand-maintained list, no server.

## The arrangement

| piece | role |
|---|---|
| `plugins/scout/skills/scout/catalog.json` | the compiled catalog (name, plugin, version, `category`, purpose, activates-when, best-for, needs, changes) — generated by `scripts/gen_catalog.py`, never hand-edited |
| `plugins/<domain>/skills/<name>/evals/result.json` | per-skill measured trigger score (`trigger.best_score`, `accuracy`, `baseline_accuracy`) |
| `scripts/gen_showcase.py` | reads the catalog + each skill's file tree (names only) + its `result.json`, emits a multi-page static site under `showcase/` |
| `showcase/index.html` | the landing page — a hero duo (`scout` + `cicero`) + a flagship row (`cerberus`, `review`, `critique`, `diagram`) + the searchable grid of all skills, filtered by **purpose `category`** (the `CATEGORY_ORDER`/`CATEGORY_LABELS` chips in `gen_showcase.py`), not by plugin namespace — a skill with a `null` category is shown in the grid but sits under no chip |
| `showcase/skill/<plugin>__<name>.html` | one page per skill (no modal) — purpose, fires-when, metrics, security scan, file tree, install, source links; plus a curated `skill/cicero.html` for the hook-only CICERO plugin, which has no `SKILL.md` |
| `showcase/assets/base.css`, `showcase/assets/dots.js` | shared styles + the interactive point-field background (theme-aware, reaches toward the cursor, honours `prefers-reduced-motion`) |
| `showcase/journal/*.html`, `showcase/assets/journal.css` | **The Journal** — hand-authored editorial articles in the house expedition-journal voice (linked from the landing's `.lede-more`), NOT generated by `gen_showcase.py`. It only ever writes `index.html`, `skill/*.html`, `base.css` and `dots.js`; the journal lives alongside that output and a regen leaves it untouched. Add or edit an article by hand; `pages.yml` deploys the whole `showcase/` tree |
| all of `showcase/**` | committed so a PR previews it; the catalog-driven part is rebuilt in CI, the journal is hand-maintained |
| `.github/workflows/pages.yml` | rebuilds and deploys the site to GitHub Pages |

## What the page shows — and what it deliberately does NOT

Shows only curated, public-safe data: id, version, purpose, when-it-fires, best-for,
side-effect tags, dependencies, the file bundle (names + sizes only), and the measured
trigger, effect (skillaxe) and security-scan metrics — each rendered only when stored in
that skill's `result.json`. The featured skills (`HERO_IDS` / `FLAGSHIP_IDS` in the
generator) carry a short curated tagline; a skill with no measured metric simply omits
that chip.

**The SKILL.md body is NOT embedded.** Bodies can carry real identifiers (namespaces,
ticket refs) and the site is public; `cerberus:leak-check` only runs on skill *edits*,
not on this export path, so a verbatim body dump would publish any pre-existing leak.
The page links to the body on GitHub instead of copying it (the mirror's bodies are
already public and leak-checked, so a future revision could render them inline; today it
links out).

**The Journal is the exception, and it is separate on purpose.** `showcase/journal/`
holds hand-authored editorial articles (the house expedition-journal voice), not
catalog-driven data — so they are prose a human wrote, reviewed like any other public
content, rather than a projection of `catalog.json`. They share the site's `base.css` +
`dots.js` and add `journal.css`; the generator neither writes nor reads them.

## The `[skip ci]` trap (why the trigger looks the way it does)

`catalog.json`'s only writer is scout-publish, which commits as
`chore(scout): regenerate catalog … [skip ci]`. GitHub Actions' `[skip ci]` suppresses
**every** push-triggered workflow on that commit, repo-wide — so a push trigger on
`catalog.json` can never fire. `pages.yml` therefore triggers on **`workflow_run`** of the
`scout-publish` workflow COMPLETING: that fires on the workflow finishing, not on its
`[skip ci]` commit's push, so the showcase rebuilds immediately after every catalog
regeneration. A **daily `schedule`** stays as a fallback, the push trigger covers the
generator/workflow/`SKILL.md` edits, and `workflow_dispatch` forces a manual rebuild.

## Change trigger

Editing `scripts/gen_showcase.py`, `pages.yml`, or what the page is allowed to show
updates this page in the same PR.
