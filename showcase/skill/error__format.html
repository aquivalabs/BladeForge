error:format v2.0.2

Enforce one Google AIP-193 style error envelope (code/status/message/details) across backend and frontend so every error is handled the same way regardless of layer.

fires when

Use when adding or handling any error path on any layer — throwing from a service/route/controller, mapping an upstream failure, or reading an error on the client (backend or frontend). Do NOT use to design the whole app's error-handling architecture — the single code-to-UX policy table (error:architecture) — or to wrap one component in a boundary or style one error tile (your framework's component skill); this skill owns the wire envelope and the reason vocabulary.

best for

Any project defining or touching an error path — a new service/route/controller throw, mapping an upstream failure, or a frontend reading an error — that wants one consistent, i18n-ready error contract instead of ad-hoc shapes per layer.
