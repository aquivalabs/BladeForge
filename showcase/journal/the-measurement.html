The Measurement

In which an expedition sets out to learn whether a skill actually works, and returns with two numbers, one that could not be trusted, and a warning it should have read sooner.

recovered from docs/mechanisms/skill-eval.md and the meta:new-skill interview · grounded in the authoring guide, not invented · English throughout

I write this for whoever inherits the gate after me. You will be tempted, as I was, to believe a skill is good because it is present — because the file exists, the description reads well, the tests are green. I believed that. I no longer do. There are two questions, and they are not the same question, and the day I learned to keep them apart is the day the measurements stopped lying to me.

Day the First— two questions, held apart

A skill is instructions we hand to the agent. We wish to know two things about it, and the whole apparatus exists to stop us from confusing them:

  • Did it fire? When a request arrives that the skill is for, is the skill reached for — and, just as important, is it left alone when the request only looks like its work?
  • Did it help? Once fired, did the guidance change the result for the better — or would the model have done the same thing unaided?

They come apart in the cruelest way. A skill can fire flawlessly and change nothing — a costume worn over the model's own instincts. Under the first metric it looks radiant. Under the second it is hollow. Merge the two numbers into one and the hollow skill borrows the radiant one's score, and you never find out. So we do not merge them. Ever.

An earlier page— the nine questions, asked before the first line

Those two questions are not first answered by a measurement. They are answered by the author, out loud, before a line of the body is written — nine of them, and the record of an expedition that skipped them is a skill that measures well and means nothing:

recovered fragment — the interview, from meta:new-skill
WHY IT EXISTS
  1a  Name ONE live occasion where it should fire. Not a category.
  1b  What comes out in that case WITHOUT it? Show it, don't describe it.
  1c  And WITH it? Show that too.

HOW IT IS USED
  2a  What has to be in place for it to work at all?
  2b  What exists at the end? Show it literally.
  2c  What checks that? Name a command — or say where to look.

THIS ONE, OR THE NEIGHBOUR
  3a  Take one query it must fire on. Who else answers it? Name them.
  3b  If someone did — which of you wins, and under what condition?
  3c  What work looks like yours but isn't? Name it, and whose it is.

Question 1b is the one that kills the skill. If the output is already fine without it, the skill should not exist — you say so and you stop. Everything downstream assumes 1b showed a real wound.

And the questions are not paperwork — each answer becomes a load-bearing part of what is later measured. 1b/1c become the eval's trigger queries. 2a/2b become the ## Contract. 2c becomes the acceptance check and rubric.json. 3b becomes the boundary sentence in the description. 3c becomes the negative eval cases — the ones that must stay quiet. The interview you answer up front IS the rubric you are graded against later; the measurement only reads back what the questions already decided.

Day the Second— the firing

Triggering is measured by a self-contained instrument, score-description.py. It reads the skill's rubric.json — an array of natural-language queries, each labelled with whether the description should make the skill fire — and it runs each one as a nested agent, watching only whether the Skill tool activates.

recovered fragment — evals/rubric.json, the trigger half
[
  {"query": "convert the px in this stylesheet to rem", "should_trigger": true},
  {"query": "make these sizes scale with the base font",  "should_trigger": true},
  {"query": "fix the border-width on this chart svg",     "should_trigger": false}
]

At least six cases, at least one of each polarity, because a test set that only proves the skill fires cannot prove it stays quiet. The score reads as a fraction — 16/18, an accuracy of 0.889 — and it is anchored to two hashes: one over the description it measured, one over the queryset. Edit either and the record marks itself stale, because the thing this eval measures is the description, and a rewritten description must not keep an old score.

One rule outranks the fraction. A negative case that fires is a real failure, whatever the skill's type. A missed positive can be forgiven in an advisory skill; a description broad enough to grab work that was never yours cannot. The narrator learned to fear the false positive more than the false negative — the former is a skill that will fire on a thousand unrelated prompts, forever, quietly.

Day the Third— the helping, and the honest trick

The second question needs a different run entirely — you cannot learn whether guidance helped by watching whether a tool fired. So acceptance is graded by a separate rite, built as skillcraft:skillaxe, an embedding-optional adaptation of SkillAxe (arXiv 2606.10546). It gives an agent a real task, lets it work with the skill, and grades the output against the acceptance half of the rubric — one yes/no per line, never one holistic 1–10 number, because a decomposed check is measurably more reliable and a single score hides which part failed.

Then comes the step that makes the whole thing honest. It runs the same task again with the skill switched off, and the grader compares the two outputs blind — not told which had the skill. Without that fourth step you cannot separate "the skill was read" from "the skill changed something", and the difference between those two is the entire reason the document exists.

recovered fragment — result.json, the acceptance half, once skillaxe has run
"acceptance": {
  "runner": "skillcraft:skillaxe",
  "method": "generate with-guide vs isolated baseline, LLM judge vs rubric acceptance",
  "quality_impact": 0.75,   // d·m, in [-1, 1] — did the guide move the result
  "skillscore": 0.92,       // instruction compliance, 0..1
  "guide_faults": ["a weak spot the guide itself owns, or none"]
}

It is deliberately not run in the gate. It spawns agents; agents are expensive and non-deterministic; a merge must not wait on a jury. So skillaxe is run locally and selectively — a high-traffic guide, a large rewrite — and roughly ten paired tasks is the floor. A difference visible only across hundreds of runs is a difference not worth the ink.

Day the Fourth— the third thing, that harms the reader

A skill runs on someone else's machine. So a third confirmation rides in the same per-skill file, written not by the scorer but by cerberus:security-scan: an eight-point consumer-safety walk — prompt-injection, exfiltration, secrets, dangerous commands, obfuscation, external fetches, credential access, privilege escalation — one verdict per point, and the whole passes only when none is flagged.

Its freshness key is broader than the trigger's, and on purpose: it hashes the skill's installer-facing material — SKILL.md, references/, and scripts/ — because a script edit changes what reaches a consumer even when the description never moves. Consumer safety has no skip flag. None. You do not get to push a skill whose safety scan is stale.

Editor's note — for those untouched by these arts
rubric.json
what a skill is measured against: the trigger queries and the acceptance claims.
result.json
what the last run measured: the trigger score, the skillaxe run (or null), the safety walk.
eval-gate
the deterministic check that blocks a touched skill whose measurement is missing or stale.
material hash
a fingerprint of everything a consumer actually runs; when it changes, the safety scan is stale.
Day the Fifth— the revelation, mundane and total

Here is the horror, and it is worse for being ordinary. For months, nothing wrote the measurement at all. The scoring had been moved to a new instrument when the marketplace replaced its upstream harness; the saving of the result did not move with it. Runs happened. They landed in *-workspace/ directories that .gitignore swallows as scratch. They evaporated. There was no evidence any skill had ever been measured.

And the gate said so, every time, honestly:

recovered fragment — what the gate printed, on everything
⚠ eval present but never measured (push allowed — refresh when you can)

Forty-two skills carried that line. It was true. It was ignored. Because a warning that appears on everything distinguishes nothing — it becomes background, weather, the hum of the fan. The mechanism whose breakage is reported as a warning breaks silently. It had been there all along. Warning. Twice a push. Seen by no one.

The survivor's protocol

What must never be done again — stated plainly, so a reader who skips the rest still leaves with every lesson.

  1. Measure two questions, never one. Firing and helping are separate metrics with separate runs. A skill that fires while changing nothing must not be able to borrow the trigger score — keep the halves in one file, scored apart.
  2. Grade acceptance against a baseline with the skill OFF. Blind, paired, same task both ways. Otherwise a green result cannot be told from a model that needed no help.
  3. One yes/no per criterion. Not a holistic 1–10. Decomposed checks are more reliable and they tell you which part failed.
  4. Fear the false positive. A negative case that fires is a real failure whatever the skill's type — a too-broad description fires forever on work that was never yours.
  5. Hash what you measure. Key each score to the exact description and queryset; key the safety scan to the installer-facing material. A rewritten thing must never keep an old number.
  6. No LLM in the gate. The blocking check is deterministic and agent-free; the jury (skillaxe) runs locally and selectively. A merge must not wait on a non-deterministic verdict.
  7. Never let breakage speak as a warning. A signal that fires on everything is silence. When a measurement is a live lie — the author is editing the very skill — make it a blocker, not a whisper.
